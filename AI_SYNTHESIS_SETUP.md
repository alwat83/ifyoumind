**Target: `ifyoumind-staging`.** Staging infrastructure was provisioned and verified on November 13, 2026. [Inventory and remaining blockers](docs/product/OPENAI_ACTIVATION_READINESS.md#controlled-staging-readiness)

- Cloud Functions, Cloud Run, Cloud Build, Artifact Registry, Eventarc and Firestore APIs are enabled. The standard Native-mode `(default)` Firestore database is in `us-central1`. Firebase Auth allows email/password, with anonymous Auth and client self-signup disabled.
- The released Firestore rules match the reviewed source. A signed-in synthetic admin and active workspace owner successfully read their membership. Staging returned HTTP 403 for anonymous quota reads and for reviewer quota reads, listing and writes. The probe left no quota record.
- The keyless `synthetic-openai@ifyoumind-staging.iam.gserviceaccount.com` runtime has a database-conditioned custom role for Firestore transactions and document get/create/update. Secret Manager accessor is granted on only `OPENAI_API_KEY`. Version 1 is enabled. The staging region has no deployed functions. Read back the deployed secret binding only after deployment authorization.

The project key is active and displays `All` permissions. An unrestricted key still inherits its owner's access. ## Staging validation after separate authorization

Use the reviewed PR #96 head and the explicit target `ifyoumind-staging`. Verify the staging Firebase app/Auth issuer, synthetic workspace, dedicated runtime account and key metadata. This phase requires specific authorization for the staging callable deploys, one synthetic invocation, the rollback deploy, and retirement of the staging key after the test. Stop if the project, identity, binding, flags, rules, membership or quotas differ from the approved plan.

1. **Deploy off.** In the ignored `functions/.env.ifyoumind-staging` file, set `SYNTHETIC_OPENAI_STAGING_PROJECT=ifyoumind-staging` and `ENABLE_SYNTHETIC_OPENAI_EXPLANATION=false`. Check that no shared dotenv file overrides the plan. Read back the existing reviewed Firestore rules release. Target only `firebase deploy --only functions:explainSyntheticMarket --project ifyoumind-staging` for the function. Review Cloud Functions and Cloud Run metadata privately. Confirm the exact runtime identity, secret project and version `1` binding to this callable, disabled flag, US Central region, 15-second timeout, two maximum instances and concurrency one. Verify that an anonymous request is rejected, and that the authorized `disabled-before` smoke returns the deterministic fixture with no quota use.
2. **Enable briefly and run once.** Record UTC start time and the staging quota counters. Use just the one authorized reviewer and change the staging flag to `true` for a targeted redeploy. Read back project, service account, bound secret version, flag and serving revision. Run one `enabled` smoke and check the result and one reservation. One invocation can perform one count and one generation request, shares a five-second provider deadline, and never retries. Stop on any failed or ambiguous result and count the attempt. Reconcile generation tokens, actual tier and attributable cost including any count-endpoint cost with the dedicated project's usage dashboard. A single latency observation is a smoke result.
3. **Restore disabled state.** Set the staging flag to `false`, redeploy the callable and confirm the disabled revision serves all traffic. Run `disabled-after` and confirm no new quota reservation or provider traffic from that call. If the disable deploy cannot be confirmed, revoke the dedicated staging key to stop new provider use and restore the known disabled configuration before another test. Revoke the staging key at the end of this one-time validation, and keep quota evidence in restricted staging records. Record only redacted results and usage counts in project handoff.

For each phase, pipe a fresh **Firebase ID token** from a trusted local staging Auth sign-in using the dedicated reviewer's credentials. Use the same approved staging Firebase project (the runner checks token audience and issuer and the server verifies its signature and authorization). The token source should write only the token on stdout and should never print it to a terminal, shell history or shared logs. The command below uses a placeholder for that local token source. A service account OAuth access token, custom token or OpenAI API key is unsuitable. [Firebase Auth REST sign-in](https://firebase.google.com/docs/reference/rest/auth#section-sign-in-email-password)

```sh
STAGING_TOKEN_SOURCE | node scripts/openai-staging-smoke.mjs --approved-staging-smoke PHASE ifyoumind-staging synthetic-WORKSPACE
```

Replace `PHASE` with `disabled-before`, `enabled` or `disabled-after` and use the existing `synthetic-market-review` workspace ID. Only the enabled phase opts in to a provider call. The other phases fail safely if the deployed flag is unexpectedly on. The runner checks the exact synthetic facts, source, caveat and fallback order. It reports latency and, on success in the enabled phase, actual generation input/output tokens and observed Standard service tier. CI runs it with mock transport. The first real staging result and a later production release each require their own approval.
