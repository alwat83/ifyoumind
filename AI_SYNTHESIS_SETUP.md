# OpenAI explanation setup

The internal \`explainSyntheticMarket\` callable sends only a fixed synthetic packet to OpenAI. It defaults off, requires an exact staging project match and blocks the production project and emulators. The production deployment allowlist excludes it. Paid Decision Reports keep their existing deterministic workflow. [Prototype review and audit](docs/product/OPENAI_ACTIVATION_READINESS.md)

## Founder setup for an authorized staging test

**Prepare only until the founder approves the target projects and spending.** The November 13 audit found only the production ifYouMind project among visible Firebase projects. The signed-in OpenAI organization was for a separate business. Confirm whether a dedicated ifYouMind staging pair exists before creating resources. Use private coordination for identifiers and credential provisioning.

1. **Firebase.** Confirm the exact dedicated project ID, Blaze billing and the approved cloud budget. Confirm Firebase Auth and an empty staging Firestore database with the reviewed repository rules. Prepare one synthetic workspace with an ID beginning \`synthetic-\`, one verified staging-only reviewer with the server-issued \`admin\` claim and an active owner/admin membership at \`intelligenceOrganizations/{id}/members/{uid}\`. Use staging-only accounts and data. Confirm that client access to \`internalExplanationQuota\` is denied. [Firebase runtime identities](https://firebase.google.com/docs/functions/manage-functions#set_a_service_account)
2. **OpenAI.** In the intended ifYouMind API organization, verify funded API access and appoint a project owner to administer a dedicated staging project. Enable \`gpt-6-luna\` and verify its project request/token limits. Confirm data-sharing and retention settings. Recommend a $1 monthly project hard limit with an alert below it, subject to founder approval and the available settings. An alert alone does not stop usage and hard limits can take time to apply. Leave organization-wide settings and other projects alone. [API billing](https://platform.openai.com/settings/organization/billing/overview) · [Model and tier limits](https://developers.openai.com/api/docs/models/gpt-6-luna) · [Spend controls](https://developers.openai.com/api/docs/guides/spend-limits)

Give it the required staging Firestore access for membership reads and quota transactions and Secret Manager accessor on only the staged \`OPENAI_API_KEY\` secret. Scope the deployer's permission to act as the runtime identity to that service account. The OpenAI project owner should create a dedicated project service-account key and restrict it to the effective permissions for Responses creation and input-token counting. Confirm both routes in the available permissions settings before giving the key broader access. The founder enters the key at the trusted Firebase CLI prompt. Keep it out of command arguments, env files, CI, chat and repository history. The second command reads only secret version metadata. Confirm the intended version is \`ENABLED\`. [OpenAI scoped keys](https://developers.openai.com/api/docs/guides/api-keys) · [Firebase secrets](https://firebase.google.com/docs/functions/config-env#secret_manager)

## Staging validation after separate authorization

Use the reviewed PR #96 head. Verify the approved staging project, Firebase app/auth issuer, synthetic workspace, dedicated runtime account and key metadata. Stop if the project, identity, binding, flags, rules, membership or quotas differ from the approved plan.

1. **Deploy off.** In the ignored \`functions/.env.STAGING_PROJECT_ID\` file, set \`SYNTHETIC_OPENAI_STAGING_PROJECT=STAGING_PROJECT_ID\` and \`ENABLE_SYNTHETIC_OPENAI_EXPLANATION=false\`, substituting the exact approved project ID. Check that no shared dotenv file overrides the plan. After confirming the staging Firestore rules separately, target just \`firebase deploy --only functions:explainSyntheticMarket --project STAGING_PROJECT_ID\`. Review Cloud Functions and Cloud Run metadata privately. Confirm the exact runtime identity, secret project/version binding to this callable, disabled flag, US Central region, 15-second timeout, two maximum instances and concurrency one. Verify that an anonymous request is rejected, and that the authorized \`disabled-before\` smoke returns the deterministic fixture with no quota use.
2. **Enable briefly and run once.** Record UTC start time and the staging quota counters. Use just the one authorized reviewer and change the staging flag to \`true\` for a targeted redeploy. Read back project, service account, bound secret version, flag and serving revision. Run one \`enabled\` smoke and check the result and one reservation. One invocation can perform one count and one generation request, shares a five-second provider deadline, and never retries. Stop on any failed or ambiguous result and count the attempt. Reconcile generation tokens, actual tier and attributable cost including any count-endpoint cost with the dedicated project's usage dashboard. A single latency observation is a smoke result.
3. **Restore disabled state.** Set the staging flag to \`false\`, redeploy the callable and confirm the disabled revision serves all traffic. Run \`disabled-after\` and confirm no new quota reservation or provider traffic from that call. If the disable deploy cannot be confirmed, revoke the dedicated staging key to stop new provider use and restore the known disabled configuration before another test. Revoke the staging key at the end of this one-time validation, and keep quota evidence in restricted staging records. Record only redacted results and usage counts in project handoff.

For each phase, pipe a fresh **Firebase ID token** from a trusted local staging Auth sign-in using the dedicated reviewer's credentials. Use the same approved staging Firebase project (the runner checks token audience and issuer and the server verifies its signature and authorization). The token source should write only the token on stdout and should never print it to a terminal, shell history or shared logs. The command below uses a placeholder for that local token source. A service account OAuth access token, custom token or OpenAI API key is unsuitable. [Firebase Auth REST sign-in](https://firebase.google.com/docs/reference/rest/auth#section-sign-in-email-password)

\`\`\`sh
STAGING_TOKEN_SOURCE | node scripts/openai-staging-smoke.mjs --approved-staging-smoke PHASE STAGING_PROJECT_ID synthetic-WORKSPACE
\`\`\`

Replace \`PHASE\` with \`disabled-before\`, \`enabled\` or \`disabled-after\` and use the lowercase staging synthetic workspace ID. The runner checks the exact synthetic facts, source, caveat and fallback order. It reports latency and, on success in the enabled phase, actual generation input/output tokens and observed Standard service tier. CI runs it with mock transport. The first real staging result and a later production release each require their own approval.
