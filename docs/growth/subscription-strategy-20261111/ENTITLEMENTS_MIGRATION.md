# Entitlements and legacy migration

**Proposed for a separate approved implementation.** New Starter and Plus entitlements are workspace-scoped. Both use the same full Decision Report, evidence, saved history and print path. Current `$79` access remains per purchased project. Current `$39` Pro continues to use its existing five-credit calendar reset on the first of the UTC month. The new paid period follows the paid Stripe invoice interval. Verify the API version and webhook object shapes during implementation. [Subscription webhooks](https://docs.stripe.com/billing/subscriptions/webhooks) · [Billing cycles](https://docs.stripe.com/billing/subscriptions/billing-cycle)

## Data and API contracts

| Record or endpoint | Required behavior |
| --- | --- |
| Server price catalog | Versioned allowlist per Stripe account and mode. Map distinct Stripe Price IDs to immutable `offerVersion`, monthly interval, USD amount and quota. Keep legacy $79 and $39 handlers separate. Resolve pilot assignment server-side. Reject unknown or wrong-mode price, workspace, role, quantity, currency or unapproved payment type. |
| Workspace billing link | One linked Stripe customer and at most one open subscription or checkout attempt per workspace. Maintain reverse lookup with uniqueness, `offerVersion`, authoritative lifecycle, current and paid-through periods, cancellation state, scheduled change and reconciliation status. An owner/admin can start billing. The client cannot write or choose Stripe IDs. |
| Paid periods | One server record keyed by subscription ID and period start, with invoice ID, supported paid line and period end, allowance, reserved and consumed counts, and grant status. Accept eligible recurring invoice lines from the pinned API. For the paid pilot require a positive settled payment on the allowlisted monthly price and successful customer/organization linkage. Unsupported discounts, prorations, zero-value/manual payments and out-of-band invoices go to review. Server timestamps use UTC and a half-open interval. Never restart a grant when an event is replayed or arrives late. |
| Credit reservation and project | Unique workspace/project reservation with period, attempt token, expiry and status. Commit reservation, unlock and immutable audit entry atomically as appropriate. Maintain existing report access markers and their semantics. Legacy access takes precedence if already unlocked. |
| Callable responses | Return typed state with offer, membership permissions, report access, available quota, pending status and paid-through/reset date. A member who may create/read a decision can spend eligible workspace credits according to existing report permissions. Billing and plan changes require the workspace owner or admin. Use existing callable validation and organization rules. No cross-tenant client reads of the billing ledger. |
| Event processing and reconciliation | Keep event IDs and a business idempotency key for each invoice, payment, reversal or cycle. Authenticate raw-body Stripe signatures and validate mode, subscription, customer and workspace. Write business changes and processed receipt in the same transaction or retryable outbox state. Retry transient failures. Record permanent mismatches with redacted identifiers and alert an operator. |

## Lifecycle and credit consumption

| Case | Customer and system behavior |
| --- | --- |
| Start Checkout | Atomically acquire a workspace checkout lease and use stable Stripe idempotency for that attempt. Reuse its existing unexpired session and canonical Customer. Refuse another subscription when the workspace has active, incomplete or dunning billing. Reconcile ambiguous expirations before issuing a replacement session. Use server-generated allowlisted return URLs. |
| Checkout completes | Link subscription and record confirmation in progress. Grant credits only after verified `invoice.paid` with an eligible paid subscription line. Support arrival before the Checkout event by validating against the preexisting workspace checkout/customer linkage, or queue/reconcile safely. Return URL success alone grants no access. |
| Paid renewal | Grant exactly once for the verified interval. Derive the interval from the qualifying invoice line and reconcile against the subscription. Check start/end boundaries on each spend, independent of scheduler or browser time. A payment received after the interval ended records revenue and audit evidence with no expired credit grant. |
| Generate or unlock | At the full-workload entry, check role, project, state, allowance and workspace/user rate limits. In a transaction reserve one credit per project, use a bounded lease, then generate outside the transaction. On successful durable report availability, finalize with the same reservation token and atomically write access and consumption. For an existing prepared report, unlock and consume in one transaction. Existing access, retry of the same finalized request, reopen and print consume zero extra. |
| Work fails or races | On a retriable provider/data failure, release the reservation idempotently with a bounded retry policy. Check the attempt token before finalizing and reject stale completions. At expiry, an accepted in-flight request may finalize only within its original bounded lease and policy, without borrowing against the new period. Reconcile orphaned reservations without reopening revoked or expired grants. Cap per workspace and per actor so free preview generation and abandoned attempts also have bounded costs. |
| Failed payment | First payment failure grants zero. Failed renewal adds no new period credits, with prior paid access to its period boundary. Show a payment-needed state and owner/admin portal recovery. Successful retry grants only its paid interval if currently valid. `past_due`, `unpaid` and retry events alone never grant. |
| Period-end cancellation | Surface the paid-through date for supported `cancel_at_period_end` and equivalent `cancel_at` schedules. Continue existing credits until that date. Confirm terminal state and expire unused credits at the paid boundary. Undo a scheduled cancellation only after provider confirmation. Stripe's terminal event may arrive later than the period boundary. |
| Upgrade/downgrade | Explicit owner/admin request with new price, count and effective date. After separate approval, schedule at renewal with no immediate proration or extra charge. Keep the old cap in the old interval and grant the new cap only after the new-price invoice settles. In the first paid pilot defer self-serve plan switching until this lifecycle passes. Use verified payment-method, invoice and cancellation functions in the portal. |
| Refund or dispute | Key a refund or dispute to its specific payment. Recommended policy for approval: full subscription reversal or open dispute holds unused credits for that paid interval, preserving unlocked reports. Partial refunds do not change credits automatically and are reviewed. A dispute win releases a hold only if the same interval remains paid and valid. Escalate confirmed fraud or legal exceptions through approved operator policy. Preserve legacy report markers. |
| Duplicate, stale and manual events | An older invoice or subscription update cannot overwrite a newer period, paid or terminal state. Re-fetch canonical provider state if ordering is ambiguous. Verify refund/dispute and reversal evidence before changing a grant. Reconcile through an authenticated, audited dry run and targeted repair by workspace/subscription. Make repairs idempotent and auditable. |

Stripe can deliver duplicates and out-of-order events. Business invariants remain in the application even if Stripe Checkout can limit concurrent subscriptions. Recheck actual cancellation, update and webhook behavior in test mode under the pinned API. [Webhook delivery behavior](https://docs.stripe.com/webhooks) · [Checkout duplicate subscriptions](https://docs.stripe.com/payments/checkout/limit-subscriptions) · [Portal configuration API](https://docs.stripe.com/api/customer_portal/configurations/create)

## Expiry and legacy protection

Expire new unused credits at the paid period boundary. Display the date before purchase and in account. One-period rollover may smooth uneven usage, but would increase maximum burst cost, create older-credit ordering and require clearer migration semantics. Indefinite banking can create a growing delivery obligation, high burst use and difficult handling on cancellation/refund. Record unmet need for rollover during the pilot before pricing that liability. Already unlocked reports are saved and visible after expiry, downgrade, cancellation and payment failure under the workspace’s existing access rules.

Grandfather $39 subscriptions in place. No bulk migration, forced cancellation or repricing. Keep their grant calculation, billing history, current plan, provider customer and subscription IDs. Keep existing $79 purchases and access markers readable, including historical records, in the old and new account UI. Retain the one-time purchase option during the pilot and label its terms. Legacy customers see the proposed offer only via a future approved, voluntary migration. Before offering it, show both allowances, the effective date, loss of legacy terms, saved-report continuity and billing changes. Reuse the Stripe customer and subscription when the provider schedule permits it. Preserve invoices and history, require explicit consent and test failures and reversals. Prevent enrollment via a second parallel subscription or second organization link to the same Stripe customer.

## Recovery and rollout constraints

Store only billing identifiers, state and amounts needed to reconcile. Protect operational and audit collections with server-only rules and limit sensitive fields in logs. Allow older clients to read unchanged legacy fields. Gate only new offers and purchase attempts during rollback. Keep paid pilot access, grant processing, invoices, portal and report reading available for enrolled customers. Disable new enrollments, freeze affected mutations, reconcile in dry-run mode and verify legacy and pilot report access before reopening. See the [backlog](IMPLEMENTATION_BACKLOG.md) for test gates.
